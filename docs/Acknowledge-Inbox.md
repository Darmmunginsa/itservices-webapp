# กล่องรอรับงาน (Acknowledge)

งานที่คนอื่นมอบหมายมาจะ**มาจ่อในกล่องนี้ก่อน** ยังไม่นับเป็นงานของเราจนกดรับ

```
งานของฉัน
┌──────────────────────────┬──────────────────────────┐
│ 📥 รอรับงาน   ③           │ [Tickets][Tasks][Incidents]│
│ ┌──────────────────────┐ │                          │
│ │ 🎫 VPN เข้าไม่ได้      │ │  งานที่รับแล้วอยู่ที่นี่     │
│ │ จาก หัวหน้า · 2 ชม.   │ │                          │
│ │ Ticket High [✓ รับงาน]│ │                          │
│ ├──────────────────────┤ │                          │
│ │ 🚨 เคสด่วน #VDI       │ │                          │
│ │ 📋 งานย่อย            │ │                          │
│ └──────────────────────┘ │                          │
└──────────────────────────┴──────────────────────────┘
```

## ทำไมต้องแยก

**"ถูกมอบหมาย" กับ "รู้แล้วและกำลังทำ" ไม่ใช่เรื่องเดียวกัน**

เดิมงานที่โยนมาโผล่ปนกับงานที่เรารับไว้แล้วทันที — แยกไม่ออกว่าอันไหนเราเห็นแล้ว
กับอันไหนมีคนโยนมาแต่เรายังไม่รู้ตัว และ**คนที่มอบหมายก็ไม่มีทางรู้ว่างานถึงมือหรือยัง**

## กติกา

| สถานะ | อยู่ไหน |
|---|---|
| ยังไม่กดรับ | **กล่องรอรับงานเท่านั้น** — ไม่โผล่ในรายการงานของเรา |
| กดรับแล้ว | ออกจากกล่อง เข้ารายการตามปกติ + **ส่งเมลแจ้งคนมอบหมาย** |

**ตัวเลขบนแท็บก็ไม่นับงานที่ยังไม่รับ** — เลขต้องตรงกับจำนวนที่เห็นในรายการ

เรียง**งานที่รอนานที่สุดขึ้นก่อน** เพราะเป็นตัวที่คนมอบหมายกำลังสงสัยว่าถึงหรือยัง

## ที่จงใจไม่เข้ากล่อง

| กรณี | เพราะ |
|---|---|
| **งานที่เราสร้างเองแล้วมอบหมายให้ตัวเอง** | เรารู้อยู่แล้ว จะให้กดรับก็ไม่มีความหมาย |
| งานที่ปิด/เสร็จแล้ว | ไม่มีอะไรให้ทำต่อ |
| งานของคนอื่น | ไม่ใช่ของเรา |

## ปุ่มรับงานมี 3 ที่ — ส่งเมลชุดเดียวกัน

1. **กล่องรอรับงาน** (หน้างานของฉัน)
2. **หน้า Ticket** — ปุ่ม "รับทราบ"
3. **การ์ด Task ในหน้าโครงการ** — ปุ่ม "รับทราบ"

ทั้งสามเรียก `services/ackNotify.ts` ตัวเดียวกัน — ถ้าต่างที่ต่างส่งเอง จะกลายเป็นว่า
กดจากบางที่แล้วคนสั่งงานไม่ได้รู้ ซึ่ง**แย่กว่าไม่ส่งเลย** เพราะคนกดเชื่อว่าแจ้งไปแล้ว

## ข้อจำกัด

- **งานเก่าที่มอบหมายไว้ก่อนหน้านี้และยังไม่เคยกดรับ จะเด้งเข้ากล่องทั้งหมด** —
  เป็นพฤติกรรมที่ถูกตามกติกาใหม่ แต่ครั้งแรกอาจเห็นเยอะ กดรับรวดเดียวได้เลย

- คนที่ไม่ใช่ Agent (ผู้แจ้งทั่วไป) จะเห็นกล่องว่างเสมอ เพราะไม่มีงานถูกมอบหมายให้

## แก้: งานที่โยนต่อข้ามกล่องรอรับงาน (พบจากการใช้จริง)

**อาการ** หัวหน้า Submit ticket แล้ว Assign ให้ปลายทาง → งานวิ่งเข้ารายการของปลายทางทันที
ทั้งที่ยังไม่ได้กดรับ

**เหตุ** ประตูรับงานเป็นแค่ของ **ตอนสร้างงานใหม่** ไม่ใช่ตอน **โยนงาน**

`IsAcknowledged: false` ถูกเขียนเฉพาะตอน create (Submit, สร้าง Task/Incident, ปฏิทิน)
ส่วนทางที่ **เปลี่ยนผู้รับผิดชอบ** ไม่มีที่ไหนล้างค่านี้เลย:

| ที่ | เดิม |
|---|---|
| หน้า Ticket → Reassign | เขียนแค่ `AssignedEmail` + ชื่อ |
| หน้า Incident → Reassign | เหมือนกัน |
| หน้าโครงการ → แก้ Task / Incident | เหมือนกัน |
| Agent Dashboard → Assign | Incident/Task ล้าง แต่ **Ticket ไม่ล้าง** |

ฉะนั้นถ้างานชิ้นนั้น **เคยถูกกดรับมาก่อน** (เช่นหัวหน้ากดรับไว้เอง) ค่า `IsAcknowledged: true`
จะติดไปกับงาน แล้วปลายทางได้งานที่ระบบถือว่า "รับแล้ว" — หลุดกล่องรอรับงานไปเลย

### ที่แก้

`assignFields(assigneeEmail, assigneeName, actorEmail, nameField)` ใน
[`src/utils/ackInbox.ts`](../src/utils/ackInbox.ts) — ตัวกลางตัวเดียว คืนสองก้อน:

- `base` — ผู้รับผิดชอบ (เขียนได้แน่)
- `ack` — เรื่องการรับงาน · **โยนให้คนอื่น = ล้างทั้งสามฟิลด์** · **มอบให้ตัวเอง = ตั้งเป็นรับแล้ว**

ชื่อและวันที่ของคนก่อนหน้าต้องล้างด้วย ไม่ใช่แค่ธง — ไม่งั้นหน้าจอจะขึ้นว่า
"รับแล้วโดย <ชื่อคนเก่า>" บนงานของคนใหม่

### ลิสต์ที่ยังไม่มีคอลัมน์

[`src/services/assignWork.ts`](../src/services/assignWork.ts) เขียนพร้อมฟิลด์ ack ก่อน
ถ้าไม่ผ่าน **เขียนซ้ำเฉพาะผู้รับผิดชอบ** แล้ว toast บอกชื่อคอลัมน์ที่ต้องไปสร้าง

ทำแบบนี้เพราะบางลิสต์ (เช่น `PM_Incidents` ที่ยังไม่ได้เพิ่มคอลัมน์) จะกลายเป็น
"มอบหมายไม่ได้เลย" ทั้งที่ตัวงานเขียนได้ — ล้มเหลวบางส่วนแล้วบอกตรง ๆ ดีกว่าล้มทั้งอัน

### พร้อมกันนั้น

เลขบนแท็บ Task / Incident ในหน้างานของฉันเคยนับงานที่ยังไม่รับด้วย ทำให้เลขไม่ตรง
กับจำนวนแถวที่เห็น (แท็บ Ticket ทำถูกอยู่แล้ว) — ตอนนี้ใช้ `mine()` ทั้งสามแท็บ

16 เทสต์คุมกฎนี้ รวมเคสที่เป็นบั๊กจริง: ธง `IsAcknowledged` ค้างจากคนก่อนหน้า

### ที่ตกไปอีกสองที่ (เจอตอนไปตรวจ Add-in)

| ที่ | อาการ |
|---|---|
| `Submit` → สร้าง **Incident** | ไม่เขียน `IsAcknowledged` เลย — เคสใหม่ข้ามกล่องรอรับงาน (Ticket/Task ทำอยู่แล้ว) |
| **Add-in** → เปิด Ticket จากอีเมล | ไม่เขียน — ticket จากอีเมลข้ามกล่อง |
| **Add-in** → เปิด Incident จากอีเมล | ไม่เขียน — เหมือนกัน |

ตอนนี้ทั้งสามใช้กฎเดียวกันผ่าน `ackOnCreate(assigneeEmail, actorEmail)`
มอบให้คนอื่น = รอรับงาน · มอบให้ตัวเอง = รับแล้ว · ไม่มีผู้รับผิดชอบ = รอรับงาน

`ackOnCreate` เขียน **แค่ธง** ไม่เขียนชื่อผู้รับกับวันที่ — ตอนสร้างยังไม่มีใครรับ
จะเขียนชื่อคนรับไปทำไม

## แก้: ไม่มีเมลแจ้ง และข้อความบอกสาเหตุผิด (พบจากการใช้จริง)

### 1. ถูกมอบหมายแล้วไม่มีเมลแจ้ง

กล่อง "รอรับงาน" ไม่มีความหมายถ้าปลายทางไม่รู้ว่ามีงานเข้า — เขาต้อง**บังเอิญ**
เปิดหน้างานของฉันถึงจะเห็น ซึ่งก็คือกลับไปเป็นการโยนงานแล้วหวังว่าอีกฝ่ายจะเจอ

เพิ่มเมล **`work_assigned`** (บอดี้อยู่ใน `email-templates-html.md` §8) ส่งเมื่อ:

| ที่ | ส่ง |
|---|---|
| หน้า Ticket → Reassign | ✅ |
| Agent Dashboard → Assign (Ticket/Task) | ✅ |
| แจ้งงาน → สร้าง Task พร้อมผู้รับผิดชอบ | ✅ |
| แจ้งงาน → สร้าง Ticket | ❌ ผู้รับผิดชอบถูก CC ใน `ticket_created` อยู่แล้ว |
| ทุกทางของ Incident | ❌ มี `incident_assigned` ที่มีบริบทของเคส (ความรุนแรง/SLA/โครงการ) |

สองฉบับเรื่องเดียวกันแย่กว่าฉบับเดียวที่ดี

### 2. "ยังไม่ได้เปิด template" ทั้งที่เปิดไว้แล้ว

การหา template เทียบ `EventKey` แบบตรงตัวเป๊ะ ๆ — **ช่องว่างท้ายบรรทัด**
หรือตัวพิมพ์ใหญ่ตัวเดียวก็หาไม่เจอ แล้วข้อความบอกว่า "ยังไม่ได้เปิด"
คนก็จะไปนั่งกดเปิดซ้ำแล้วก็ยังไม่ได้ผล

และข้อความเดียวกันนี้ยังถูกใช้กับอีก 2 กรณีที่ต่างกันสิ้นเชิง:

| สภาพจริง | เดิมบอกว่า | ตอนนี้บอกว่า |
|---|---|---|
| ไม่มีแถวเลย | ยังไม่ได้เปิด template | ไม่พบแถว EventKey นี้ (มีทั้งหมด N แถว) |
| มีแถวแต่ปิดอยู่ | ยังไม่ได้เปิด template | มีอยู่ แต่ช่อง IsEnabled ถูกปิดไว้ |
| เปิดแล้วแต่ Subject/Body ว่าง | ยังไม่ได้เปิด template | เปิดอยู่ แต่ช่อง Subject/Body ว่าง |
| พิมพ์ EventKey ผิดนิดเดียว | ยังไม่ได้เปิด template | ไม่พบ "x" — ที่ใกล้เคียงในลิสต์: y, z |

พร้อมกันนั้นทำให้การหาทนขึ้น: **ตัดช่องว่าง + ไม่สนตัวพิมพ์** และ `IsEnabled`
รับได้ทั้ง Yes/No, Choice และ Text (`"Yes"` / `"ใช่"`) · **ถ้าไม่มีคอลัมน์นี้เลย
ถือว่าเปิด** เพราะการมีแถวอยู่ก็คือความตั้งใจจะใช้แล้ว ดีกว่าเงียบเพราะคอลัมน์ที่ไม่มีอยู่จริง

### 3. หน้า Diagnostic ตรวจ template ให้เอง

หน้า Diagnostic เพิ่มแถบ **Template อีเมล** ไล่ตรวจ EventKey ทั้ง 7 ตัวที่โค้ดเรียกใช้
**ด้วยฟังก์ชันเดียวกับตอนส่งจริง** — ถ้าเขียนกฎใหม่ให้หน้านี้ มันจะบอกว่าผ่าน
ทั้งที่ส่งจริงแล้วไม่ออก

บอกด้วยว่า EventKey มีช่องว่างหน้า/หลังหรือไม่ (ระบบทนให้ แต่มองด้วยตาไม่เห็น)

`emailService` เพื่อให้ทดสอบใน node ได้ (19 เทสต์)
